1
Triage by Severity
Sub-tasks 1.1 – 1.5
Human review on escalation
Input
  • Unstructured claim text (up to 50,000 chars)
  • Source channel: EMAIL / PHONE_TRANSCRIPT / WEB_FORM
  • policy_id (from form or extracted from text)
  • loss_date (from form or extracted)
Agent Task
1.1
Parse & extract structured attributes
Extracts: policy_id, loss_date, loss_description, claimant email, estimated loss value, claim narrative. Assigns parse_confidence 0–1.
AGENT_ONLY
1.2
Classify claim type
MOTOR / PROPERTY / LIABILITY / HEALTH / OTHER. classification_confidence 0–1. Threshold: ≥ 0.85 → AGENT_LOG; < 0.85 → AGENT_REVIEW, 30-min window.
AGENT_LOG ≥ 0.85 AGENT_REVIEW < 0.85
1.3
Assess severity — LOW / MEDIUM
severity_score 0–59. Uses claim type, estimated loss value, narrative signals. No escalation — proceeds directly to TRIAGED.
AGENT_LOG
1.4
Assess severity — HIGH / CRITICAL
severity_score ≥ 60. Creates EscalationBriefing. 30-min specialist review window. Consequence of downward misclassification affects regulatory SLA.
AGENT_REVIEW EscalationBriefing
1.5
Detect special handling flags
Scans for: FATALITY, LEGAL_REPRESENTATION, VULNERABLE_CLAIMANT, FRAUD_INDICATOR. Any flag → 15-min review window. False negative cost is asymmetric (regulatory breach).
AGENT_REVIEW 15-min window
Output
  • ClaimRecord created (PARSED or PARSE_UNCERTAIN)
  • claim_type + classification_confidence
  • severity + severity_score
  • special_handling_flags[]
  • parse_confidence score
  • EscalationBriefing (if 1.4 or 1.5 triggered)
PARSED PARSE_UNCERTAIN TRIAGED TRIAGE_PENDING_REVIEW
Human Review
  • parse_confidence < 0.70 → PARSE_UNCERTAIN; specialist corrects extracted fields; processing halted until re-parsed
  • classification_confidence < 0.85 → specialist confirms or corrects claim_type within 30 min
  • severity HIGH / CRITICAL → specialist confirms or reclassifies within 30 min
  • Any special flag → specialist confirms or dismisses within 15 min; false positive cost is low; false negative cost is high
  • Window expiry without action → Claim.status = ESCALATED; SLA warning fires
2
Validate Against Policy Coverage
Sub-tasks 2.1 – 2.6 · Contains HUMAN_ONLY boundary at 2.6
Governance control at 2.6
Input
  • ClaimRecord (status = TRIAGED)
  • policy_id extracted from claim
  • loss_date
  • claim_type (confirmed at step 1)
Agent Task
2.1
Retrieve policy record (SOAP)
Read-only call to legacy policy administration system. No decision made. Retry 3× on failure → INTEGRATION_ERROR.
AGENT_ONLY
2.2
Validate policy in-force at loss_date
Checks policy_status = IN_FORCE AND policy_start_date ≤ loss_date ≤ policy_end_date. Binary determination; auditable and traceable.
AGENT_LOG
2.3
Match coverage — high confidence
coverage_match_confidence ≥ 0.85 AND exclusion_candidates = []. Unambiguous match. Logged; no human review. Adjuster will catch mismatches.
AGENT_LOG → COVERAGE_CONFIRMED
2.4
Match coverage — ambiguous (0.70–0.84)
Plausible match but cannot rule out alternative interpretations. Wrongly accepting or rejecting creates financial or regulatory exposure. 30-min review window.
AGENT_REVIEW 30-min window
2.5
Apply coverage exclusions check
Identifies candidate exclusion clauses. Exclusion language requires professional judgment; incorrect application triggers formal dispute. Agent identifies; specialist confirms.
AGENT_REVIEW 30-min window
2.6
Coverage dispute resolution
coverage_match_confidence < 0.70 OR status = DISPUTED. Agent provides structured briefing note only. No agent action until human decision logged.
HUMAN_ONLY
Output
  • policy_status (IN_FORCE / LAPSED / UNCERTAIN)
  • coverage_match_confidence score
  • exclusion_candidates[]
  • coverage_status: COVERED / NOT_COVERED / UNCERTAIN / DISPUTED
COVERAGE_CONFIRMED COVERAGE_PENDING_REVIEW COVERAGE_DISPUTED COVERAGE_LAPSED
Human Review
  • 2.4 ambiguous → specialist reviews coverage determination + policy clause within 30 min; logs decision with reviewer_id
  • 2.5 exclusion → specialist confirms or rejects each candidate exclusion within 30 min; logs with clause reference
  • 2.6 HUMAN_ONLY → senior specialist assigned; no agent action until decision logged; coverage decision is professionally accountable act
  • COVERAGE_LAPSED → senior specialist via CRM review queue
  • Window expiry → ESCALATED; sla_breached flagged if no resolution
⚠ Governance boundary — 2.6 Coverage Dispute Resolution is HUMAN_ONLY. Two independent reasons: (1) Reversibility — once communicated to the claimant, retracting a coverage decision triggers a regulated formal dispute process. (2) Professional accountability — coverage interpretation is a regulated professional act; the signing specialist is personally accountable. The boundary can only move if the client provides evidence that confidence ≥ 0.85 means "effectively certain" against their actual policy data.
3
Route to Adjuster
Sub-tasks 3.1 – 3.4 · Requires COVERAGE_CONFIRMED
Fully automated (QUEUE_OVERFLOW excepted)
Input
  • ClaimRecord (status = COVERAGE_CONFIRMED)
  • claim_type (confirmed)
  • AdjusterQueueEntry[] from CRM — specialty, queue_depth, is_available
Agent Task
3.1
Derive required adjuster specialty
Deterministic lookup: MOTOR→MOTOR · PROPERTY→PROPERTY · LIABILITY→LIABILITY · HEALTH→HEALTH · OTHER→GENERAL. No judgment required.
AGENT_LOG
3.2
Select adjuster from queue
Filters candidates by specialty + is_available = true. Selects lowest current_queue_depth. Workload optimisation — no judgment, no claimant-facing consequence.
AGENT_ONLY
3.3
Write ClaimAssignment to CRM
HTTP POST to CRM. HTTP 201 required before Claim transitions to ROUTED. Timestamp logged — used to measure adjuster SLA. Retry 3× on failure.
AGENT_LOG
3.4
Send adjuster notification via CRM
Standardised notification: claim reference, severity, receipt timestamp, claim summary. Fires within 60 s of ClaimAssignment creation. Fully reversible if routing corrected.
AGENT_ONLY
Output
  • ClaimAssignment record (adjuster_id, specialty, queue_depth_at_assignment)
  • Adjuster CRM notification
ROUTED QUEUE_OVERFLOW

QUEUE_OVERFLOW: no adjuster with required specialty available. Agent retries every 5 min for 60 min before SLA breach warning fires.

Human Review
  • QUEUE_OVERFLOW → specialist manually assigns adjuster within 60-min window
  • Agent retries automatically every 5 min; specialist can pre-empt with manual assignment
  • After 60 min with no assignment, SLA breach warning fires to operations team
  • Specialist can override adjuster selection at any point; creates new ClaimAssignment; old record superseded for audit
4
Acknowledge to Claimant
Sub-tasks 4.1 – 4.3 · 4.1 fires unconditionally within 5 min of receipt · 4.3 is HUMAN_ONLY
Governance control at 4.3
Input
  • ClaimRecord.created_at (for 5-min ACK timer)
  • ClaimRecord.external_reference
  • ClaimRecord.status (ROUTED for 4.2)
  • special_handling_flags[] (gates 4.2)
  • Adjuster name + contact channel (CRM, for 4.2)
  • EscalationBriefing (for specialist 4.3)
Agent Task
4.1
Send receipt acknowledgement
Fires within 5 min of ClaimRecord creation, unconditionally — before triage, before coverage, before routing. Contains: external_reference, receipt confirmation, 2-hour SLA commitment. Must NOT include coverage status or adjuster identity.
AGENT_ONLY ≤ 5 min · unconditional
4.2
Send routing confirmation (standard claims)
Fires on ROUTED AND special_handling_flags = []. Contains: adjuster name, contact channel, expected contact timeframe. Suppressed if any flag is set — specialist handles instead.
AGENT_LOG Suppressed if flags ≠ []
4.3
Escalation / special-handling communication
Fires when ESCALATED or special_handling_flags ≠ []. Agent role: generates structured EscalationBriefing note only. Specialist drafts and sends all claimant-facing content.
HUMAN_ONLY
Output
  • AcknowledgementRecord (RECEIPT) — always
  • AcknowledgementRecord (ROUTING_CONFIRMATION) — standard claims only
  • EscalationBriefing note — for specialist use in 4.3
ACKNOWLEDGED COMPLETED

4.1 delivery failure: one retry immediately; if failed → manual-send queue + specialist notified within 5 min.

Human Review
  • 4.1 delivery failure → specialist sends manual ACK within 15 min
  • 4.3 HUMAN_ONLY — specialist drafts and sends all escalation / delay / special-handling communications
  • LEGAL_REPRESENTATION flag: communication must go via claimant's solicitor, not directly to claimant
  • Vulnerable claimant: tone + content governed by client vulnerable customer policy (not templatisable)
  • Agent provides structured briefing note; specialist has full discretion over message content and channel
⚠ Governance boundary — 4.3 Escalation Communications are HUMAN_ONLY. Messages about delays or special handling carry (1) jurisdictional obligations on what can be said, (2) vulnerable customer policy requirements on tone and channel, and (3) for LEGAL_REPRESENTATION cases, mandatory indirect communication rules (solicitor only). These obligations vary by case and cannot be reliably encoded in a template. The specialist who owns the escalation owns the communication that follows it.
