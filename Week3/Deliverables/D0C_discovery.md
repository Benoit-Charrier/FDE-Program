# Deliverable D0C — Discovery: MedFlex Clinical Workforce Staffing

*Source: `Scenario/scenario_context.md`, `References/1-atx-assessment.md`, `References/discovery-questioning-patterns.md`. All numbers trace to scenario_context.md or are labelled as assumptions. DS-confirmed items reflect the mid-week discovery session with Marcus Reyes (CEO).*

---

## 0. Executive Summary

- **Primary cognitive workload:** WS2 (nurse-to-shift matching) consumes the most skilled human time — structured matching data (credentials, availability, proximity, hospital and nurse preferences) is stored in a database [DS-confirmed], but at ~120 decisions/coordinator/day the cognitive burden lies in the judgment layer applied on top: resolving edge cases not in the data, applying facility-specific heuristics that are undocumented and vary across all 8 coordinators, and managing the multi-submission race condition in real time; coordinator judgment — not data access — is the binding constraint on fill rate.
- **Most critical lived-vs-documented gap:** Confirmation is documented as a closed loop but is structurally passive — nurse silence is treated as acceptance, and no-shows are discovered exclusively by hospital call at or after shift start [DS-confirmed]; the 12% no-show rate is a consequence of this design, not a coordinator execution failure, and cannot be reduced without redesigning the confirmation model to require active acknowledgement and adding a pre-shift monitoring layer.
- **Highest-signal delegation opportunity:** WS2 "clean" fills — placements where credentials are valid, no profile notes, and nurse accepts first contact — are the strongest agent candidate; with nurse matching data confirmed as structured and database-queryable [DS-confirmed], the primary remaining pre-conditions are structured facility preference profiles and a HITL validation phase to build coordinator trust before reducing oversight.

## 1. Lived Process Narrative

*Reconstructed from scenario_context.md. Steps marked [scenario] are directly stated. Steps marked [DS-confirmed] are confirmed by the mid-week discovery session. Steps marked [assumption — AD#] are inferred and logged in Section 6.*

**The shift fill cycle — from request to confirmed placement:**

A shift request arrives at MedFlex via email (dominant channel [DS-confirmed]), portal, or phone. All intake arrives as **unstructured free text** regardless of channel [DS-confirmed] — there is no structured intake form at point of receipt. The request lands in ServiceNow, which functions as a queue manager. There is no stated routing or prioritisation logic; coordinators pick up requests when they have bandwidth. [assumption — AD1] For a same-day or urgent shift, this creates an unmanaged queue dynamic: the shift sits until a coordinator reaches it, during which time a competitor agency may be filling the same role.

**Pause point — requirement extraction:** The coordinator reads the free-text request and extracts matching criteria: unit type, required specialty, date/time, facility preferences. If the specialty is ambiguous (e.g., "ICU experience preferred" vs. "ICU certification required"), the coordinator interprets it. This interpretation is not standardised — eight coordinators will parse the same ambiguous request eight different ways. [DS-confirmed: 8 coordinators = 8 undocumented judgment calls]

**Judgment call — candidate identification:** The coordinator queries the **nurse database** — a structured system containing nurse profiles, credentials, availability, and qualification requirements as separate entities [DS-confirmed]. The database provides the facts; the coordinator's judgment determines what to do with edge cases on top of those facts: which nurse performs well at this specific facility, whether a borderline-credential profile the facility has historically accepted will work again, which nurse is reliable enough for a short-notice shift. This judgment layer is undocumented, not in the database, and varies materially by coordinator tenure — experienced coordinators resolve edge cases in seconds; newcomers take longer and sometimes make worse calls. [DS-confirmed]

**Workaround — multi-submission race condition:** Because hospitals submit shift requests to multiple staffing agencies simultaneously [DS-confirmed], coordinators submit the same nurse to multiple facilities to win the placement before a competitor does. This is a deliberate competitive coping strategy. After receiving a confirmation from one facility, the coordinator must manually withdraw the nurse from remaining open submissions. If multiple facilities confirm the same nurse before withdrawal is processed, MedFlex must apologise and withdraw — damaging the facility relationship. The downstream cost (coordinator rework, facility friction, potential placement loss) compounds at ~960 decisions/day volume. [DS-confirmed]

**Credential gate — coordinator role:** The coordinator reads the pre-verified credential status from the nurse's profile in the database. They do not perform credential verification themselves — that is owned by a separate compliance/legal team [DS-confirmed]. If the profile shows valid credentials for the required specialty and placement state, the coordinator proceeds. If the nurse profile contains specific notes (facility-specific restrictions, prior incidents, preferences), this is the trigger for elevated human review at the matching step. [DS-confirmed]

**Async wait — passive confirmation loop:** The coordinator submits the selected nurse to the facility. The nurse receives an SMS or email notification [DS-confirmed]. Silence is treated as acceptance — the nurse must actively call in to reject. This passive confirmation design means a nurse who did not see the notification is indistinguishable from one who accepted and intends to appear. Notifications are sent 2–3 days before the shift; a 24-hour cancellation rule applies. [DS-confirmed]

**No-show discovery — zero proactive detection window:** No-shows are discovered exclusively when the hospital calls MedFlex to report the nurse did not appear [DS-confirmed]. There is no pre-shift confirmation check, no monitoring of acknowledgement status, and no proactive re-fill trigger. By the time a no-show is known, the shift window has already opened — the remediation window is effectively zero.

**What the SOP says vs. what actually happens:**

| SOP layer | Lived layer |
|-----------|-------------|
| Receive shift request | Receive unstructured free text; coordinator interprets and extracts requirements |
| Credential gate before matching | Read pre-verified status from database; compliance team maintains profiles |
| Match nurse from system records | Query database → apply undocumented judgment overlay (quality varies by coordinator tenure) |
| Submit one candidate per shift | Multi-submit same nurse to multiple facilities simultaneously (competitive coping strategy) |
| Obtain structured confirmation | Passive notification (SMS/email); silence = accepted |
| Pre-shift confirmation | No proactive monitoring; no-show discovered by hospital call at shift start |

The gap between documented and lived process is not a compliance failure by individual coordinators — it is a structural consequence of 120 decisions/day volume, competitive market time pressure, and a confirmation model that was never designed for the current operation scale.

**Pain level justification:**
- **WS2 (H):** 120 decisions/day with a judgment overlay that varies across 8 coordinators; outcome data (4.2-hour fill time vs. 1-hour target, 7% mismatch rate) confirms throughput bottleneck and quality degradation. Highest-volume, highest-consequence work stream.
- **WS4 (H):** Passive confirmation model is a confirmed design failure — 12% no-show with zero proactive detection is structurally addressable; each no-show is a facility relationship event and revenue failure. High volume, direct remedy available.

- **WS1 (M):** Intake is high-volume but low cognitive complexity; free-text parsing creates friction but the act of receiving and routing a shift request does not require skilled judgment.
- **WS3 (L for coordinators):** Compliance verification is out of coordinator scope — coordinators read a pre-verified database status. Credential data freshness is a compliance team dependency, not a coordinator automation target.

**Note — work stream where agent is not warranted:**
WS1 intake from the portal channel is deterministic: a structured form submission with known fields can be parsed, validated, and queued by **RPA or static rules** without an agent. Building an agent for portal intake would introduce engineering overhead without commensurate value. Agent investment belongs in WS2 and WS4, where non-determinism and judgment are present.

## 4. Cognitive Workload Hotspots

> **Hotspot [WS2-1]:** Nurse-to-shift matching — judgment layer over structured data
> **What the human does:** Queries the nurse database for candidates matching the structured requirements (credentials, availability, proximity) [DS-confirmed], then applies institutional knowledge for edge cases the data does not resolve: which nurse performs well at this specific facility, whether a borderline-credential profile will be accepted, which nurse is reliable enough for a short-notice submission. The cognitive act is the judgment layer on top of structured data — not finding the data itself.
> **Why a machine can't trivially replace this today:** The judgment heuristics are undocumented, vary across 8 coordinators, and are not encoded in the database [DS-confirmed]. Facility-specific preference profiles — which nurses a facility prefers or avoids — are an open unknown [U-3]. The agent can match on hard rules; it cannot apply soft preferences without structured facility profiles.
> **Delegation signal:** High for clean fills — database is structured and queryable, so credential and availability matching can be applied directly. Delegatable when: (1) facility preference profiles are structured and current [U-3], (2) clean-fill criteria explicitly defined (no profile notes, standard credentials, available nurse). HITL required in phase 1 to validate agent judgment before reducing oversight — prior recommendation engine failure confirms coordinator trust must be built before autonomy is expanded [DS-confirmed: A13].

> **Hotspot [WS2-2]:** Multi-submission withdrawal management
> **What the human does:** After submitting the same nurse to multiple facilities simultaneously, monitors incoming confirmations in real time and withdraws the nurse from remaining open submissions on first acceptance. When multiple confirmations arrive before withdrawal is processed, manages the apology-and-withdrawal workflow with the affected facility while tracking remaining open shifts in the queue.
> **Why a machine can't trivially replace this today:** Multi-submission monitoring requires real-time tracking of all open submissions per nurse — a manual, attention-intensive task at 960/day volume. The apology-and-withdrawal workflow involves relationship judgment that varies by facility tier and history. At current volume, manual management creates compounding rework risk.
> **Delegation signal:** Real-time status monitoring and automated withdrawal notification are tractable agentic orchestration — primarily execution, not judgment. Relationship management when the race condition fires stays human. This is a strong near-term automation target independent of the matching quality question; it addresses coordinator rework directly and has a clear, deterministic trigger (first confirmation received).

> **Hotspot [WS4-1]:** Placement confirmation — passive model and zero pre-shift detection
> **What the human does:** Under the current passive model, the coordinator does nothing active after submitting the shift — silence is treated as accepted. Cognitive work occurs reactively: when the hospital calls to report a no-show, the coordinator must manage the facility relationship, find a replacement under time pressure, and update records — while the full shift queue continues to demand attention.
> **Why a machine can't trivially replace this today:** Proactive pre-shift confirmation detection does not currently exist as a process or system. An agent that monitors confirmation status, sends structured re-confirmation requests for unacknowledged placements, and escalates to the coordinator before the shift window opens would require a process redesign — not just automation of an existing step.
> **Delegation signal:** High — a structured active confirmation loop is deterministic. Agent sends structured confirmation request (SMS/email); tracks response; escalates unacknowledged placements to coordinator X hours before shift start; triggers re-fill workflow on confirmed no-intention-to-appear. The notification-failure portion of the 12% no-show rate is directly addressable [scenario_context: A3]. Replacement-finding after a confirmed no-show requires human decision.

> **Hotspot [WS2-3]:** Portfolio reprioritisation under competitive time pressure
> **What the human does:** When the optimal candidate is unavailable or the first-choice facility is lost to a competitor, the coordinator must reprioritise across all open shifts simultaneously — not just the individual shift — while knowing that response speed determines whether MedFlex wins or loses the placement. Urgency scoring and facility priority tiers are applied in real time, based on criteria that are not codified.
> **Why a machine can't trivially replace this today:** Portfolio reprioritisation requires urgency scoring and facility priority tiers that are not stated as structured in any system — these criteria are relationship-based and assumed partially tacit [assumption AD1]. The competitive time pressure creates a "good enough fast" operational requirement; an agent that takes longer than a coordinator to surface alternatives loses the placement regardless of match quality.
> **Delegation signal:** Delegatable when shift urgency scoring and facility priority tiers are explicitly configured. Until then: agent surfaces ranked alternatives from the database immediately; coordinator retains the triage decision. Speed of candidate surfacing is the primary value proposition — the agent removes the database query time so the coordinator can apply judgment faster.

## 5. Known Unknowns

> **Unknown [U-1]:** What is the actual latency between a real-world credential event (licence renewal, certification completion, background check result) and the nurse database record update — and what SLA governs the compliance team's update process?
> **Why it matters for agent design:** If credential data in the database is 24–72 hours stale, the agent cannot enforce the credential gate reliably — stale-positive errors permit uncredentialed placements; stale-negative errors block valid ones. The compliance team owns the update process [DS-confirmed]; their data freshness SLA is a critical integration dependency for the matching agent. A "credential status uncertain" routing path may be required if no SLA exists.
> **How to discover it:** Ask compliance team: "When a nurse renews their licence, how quickly does that appear in the nurse database? What triggers the update — is it manual, or does the system pull from state registries?" Pull a sample of recent credential update timestamps vs. licence renewal dates.

> **Unknown [U-2]:** What percentage of shift fills are "clean" — first-contact accept, no credential gaps, no profile notes, standard specialty — vs. requiring exception handling?
> **Why it matters for agent design:** The automation opportunity for WS2 is concentrated in clean fills. If clean fills are 70%+ of volume, the agent handles the majority autonomously; if exception fills dominate, exception handling must be in agent scope from v1 — a substantially larger and riskier build.
> **How to discover it:** Ask coordinators to walk through the last 10 shifts filled and count how many required more than one nurse contact, had a credential gap, or had a profile note. Pull placement records and count contact attempts per filled shift.

> **Unknown [U-3]:** Are facility-specific preference profiles (required specialty, certification requirements, unit-specific orientation, historical override tolerance, nurse reputation notes) structured and queryable in a system — or do they exist primarily in coordinator memory?
> **Why it matters for agent design:** The nurse database is confirmed as structured for nurse-side data [DS-confirmed], but facility-side preference data is an open unknown. The agent can match on hard credential rules; it cannot apply facility-specific soft preferences or reputation-based selection without structured facility profiles. This is the primary remaining pre-condition gap for full WS2 delegation.
> **How to discover it:** Ask to view the facility profile record for one hospital in the current system. Probe: "When a facility adds a new certification requirement or tells you they no longer want a specific nurse, how does that get into your records? Is there a structured field for nurse preferences or past feedback per facility?"

> **Unknown [U-4]:** How is after-hours shift coverage managed — is there a dedicated on-call coordinator, and does fill rate decline materially outside business hours?
> **Why it matters for agent design:** After-hours is the highest-ROI initial deployment target if coordinator bandwidth drops to one on-call person. If after-hours fill rate is significantly lower than business hours, that is the strongest single business case for the agent — current process is already degraded, so displacement risk is minimal and incremental improvement is high.
> **How to discover it:** Ask: "What happens when a shift request comes in at 2am on a Sunday? Who handles it?" Request fill rate data segmented by time of day and day of week if available.

> **Unknown [U-5]:** What is the split between the two root causes of the 7% mismatch rate — actual credential mismatch vs. hospital preference/reputation-based rejection?
> **Why it matters for agent design:** If mismatch is primarily credential-based, the agent's credential gate directly addresses the problem. If mismatch is primarily hospital preference-based, structured facility profiles are required — a harder and longer prerequisite. Targeting a 7% → 0% reduction without knowing the split will produce a spec that oversizes or undersizes the credential gate.
> **How to discover it:** Ask Marcus or coordinators: "When a facility rejects a submission, do they typically cite a credential gap or a preference issue? Of the last 10 mismatches, how many were hard credential failures vs. 'we prefer not to work with this nurse'?"

> **Unknown [U-6]:** What is the technical form of the nurse database — is it a ServiceNow module or a separate system, and does it have an accessible API?
> **Why it matters for agent design:** The nurse database is confirmed as structured [DS-confirmed], but its technical identity — ServiceNow module, separate ATS, or other system — is unknown. An agent that can query the nurse database directly via API can perform real-time candidate lookup; an agent that must go through ServiceNow screen-level interaction or a coordinator intermediary faces integration complexity. This determines the build approach for the matching capability.
> **How to discover it:** Ask: "Is the nurse database part of ServiceNow or a separate system? Can you show me a nurse profile — what fields are there? Is there an API or integration available for reading nurse records?"

> **Unknown [U-7] — PARTIALLY RESOLVED [DS-confirmed]:** Whether compliance verification is performed by coordinators or a separate team — *resolved*: separate compliance/legal team confirmed [DS-confirmed]. **Remaining unknown:** What does the handoff interface look like between compliance database updates and coordinator database reads? Is there a defined SLA for profile freshness? Is there an escalation path when a coordinator encounters a profile that appears stale?
> **Why it matters for agent design:** The matching agent's credential gate depends on the compliance team's update cadence. If there is no defined SLA or escalation path, the agent must include a "credential status uncertain" routing that holds the placement for human review rather than auto-blocking or auto-approving.
> **How to discover it:** Ask: "When a coordinator notices a nurse profile where the credential renewal is coming up — say, it expires next week — what do they do? Is there a way to flag to the compliance team that an urgent recheck is needed?"
